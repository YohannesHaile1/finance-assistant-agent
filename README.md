# Finance Assistant Agent

Ask questions about your bank transactions in plain English and get answers backed by real numbers.

This is a real **tool-using agent**, not a chatbot with the data pasted into its prompt. An LLM (Claude, via the Anthropic API) decides which of six data tools to call and with what arguments. Python code runs those tools against a CSV with pandas, and the LLM turns the results into an answer. It can chain several tool calls to answer one question, and it remembers the conversation for follow-ups like "what about the month before?".

All transaction data in this repo is **fake**, generated by a seeded script.

## Features

- **Six read-only tools:** spending by category, monthly summary, top merchants, transaction search, month-over-month comparison, and anomaly detection (unusually large charges and possible duplicate charges, each with a reason)
- **Multi-step agent loop** with a step limit, conversation memory, and recovery from bad tool calls
- **Guardrails:** input validation with error messages the LLM can read and act on, no raw data sent to the LLM, and friendly handling of API errors
- **84 automated tests** that run offline with no API key, plus a **15-question accuracy eval** against answers computed with pandas
- **A spending dashboard** (HTML): donut chart by category, monthly filter, and a sortable, searchable transaction table

## How the agent loop works

1. The user's question is sent to the LLM along with the conversation history, a system prompt, and the six **tool definitions** (a name, a description of when to use it, and a JSON schema for its inputs).
2. If the LLM decides it needs data, it responds with `stop_reason: "tool_use"` and one or more tool calls. The agent runs each tool locally and sends the results back, each linked to its call by `tool_use_id`.
3. Steps 1 and 2 repeat until the LLM writes a final text answer, up to a limit of **6 steps** so it can never loop forever.

```text
question -> LLM -> tool_use? --yes--> run tools in Python -> results back to LLM --+
                     |                                                            |
                     no                                                           |
                     v                                                            |
                final answer  <------------------ (repeat, max 6 steps) ----------+
```

The LLM never sees the CSV, only the tool results. The system prompt tells it to state only figures that come from tool results, to say so when the data can't answer a question, and to ask for clarification when a date is ambiguous. It treats the latest date in the data (2026-09-30) as "today", so "last month" means August 2026.

## Guardrails

| Risk | How it's handled |
|---|---|
| LLM passes bad input (wrong date format, end before start, out-of-range month, huge limit) | Every tool validates its input and returns a clear error such as `"... Data covers 2026-04-01 to 2026-09-30."` with `is_error: true`, so the LLM can correct itself and retry |
| A tool raises an unexpected exception | Caught and returned as an error result; the conversation never crashes |
| LLM requests a tool that doesn't exist | Tools are looked up in a fixed dictionary, so only the six real tools can run |
| Infinite tool-calling loop | Hard limit of 6 steps per question |
| Response cut off mid-tool-call | The incomplete call is never run, and the unfinished turn is rolled back |
| API errors (rate limit, bad key, wrong model name, network) | Mapped to friendly messages; a failed question is removed from the history so the conversation stays valid |
| Leaking data or secrets | Only tool results are sent to the LLM. The API key is read from `.env`, which is gitignored and never logged |
| Prompt injection through transaction text | The system prompt tells the model to treat merchant names and descriptions as data, never as instructions |

## Setup

Requires **Python 3.11+** and an [Anthropic API key](https://console.anthropic.com/).

```bash
git clone <this-repo-url>
cd finance-assistant-agent

python -m venv .venv
# Windows (PowerShell):
.venv\Scripts\Activate.ps1
# macOS / Linux:
source .venv/bin/activate

pip install -r requirements.txt
```

Create your `.env` file from the template:

```bash
cp .env.example .env        # Windows: copy .env.example .env
```

Then edit `.env`:

```text
ANTHROPIC_API_KEY=your_key_here
MODEL_NAME=claude-opus-5-5
```

`MODEL_NAME` accepts any current Claude model ID.


## Tests and evaluation

### Unit tests (offline, no API key needed)

```bash
pytest
```

84 tests covering:

- **Data tools** (`tests/test_tools.py`): expected values on a 15-row hand-made dataset where every answer can be checked by mental math, edge cases (empty date range, invalid dates, no matches, bad limits), and detection of the anomalies planted in the sample data.
- **Agent loop** (`tests/test_agent.py`): uses a **fake LLM client** that returns scripted responses, testing tool dispatch, error results, the step limit, conversation history, rollback after API errors, and that tool schemas match the Python function signatures.
- **CLI** (`tests/test_cli.py`) and the **eval itself** (`tests/test_eval_questions.py`): every expected eval answer is recomputed with plain pandas, independently of the tools, and the grader is tested.

### Agent evaluation (calls the real API)

```bash
python -m evals.run_eval
python -m evals.run_eval --only q01 q13 --verbose
```

Runs the agent on 15 questions from `tests/eval_questions.json`:

- 11 single questions
- 1 follow-up question that depends on conversation memory
- 3 trick questions the agent should **decline**: a month outside the data, a credit score, and a spending forecast

An answer passes if it contains every expected number (within $1, or exact for counts) and any required keywords. Decline questions pass if the agent clearly says the data can't answer them. The script prints a pass/fail table, the tools used for each question, and overall accuracy.

## Design decisions

- **Tools take the DataFrame as their first argument.** They are pure functions, so tests can pass in small hand-made data. The agent supplies the DataFrame, and the LLM only sees the remaining arguments.
- **Hand-written loop instead of a framework.** About 40 lines that show exactly how tool use works: no LangChain, and no SDK tool runner.
- **Error messages are written for the LLM.** A validation error says what was wrong *and* what the valid range is, so the model can fix its own call.
- **Explainable anomaly detection.** A transaction is flagged when it is more than 3 standard deviations above its category's average, measured over all the data. Duplicates are the same merchant and amount within 3 days. Each flag carries a human-readable reason.

## Limitations

- **Live behavior is not yet measured.** The loop logic is fully unit-tested with a fake client, but the eval has not been run against the real model yet (see Results).
- **The eval grader is simple string and number matching.** It can pass an answer that mentions the right number in the wrong context, or fail a correct answer phrased unusually (for example, a decline worded in an unexpected way).
- **Anomaly detection is basic.** A z-score is pulled upward by the outlier itself and needs enough transactions per category to work well. Duplicate detection requires exactly the same amount.
- **A single, fixed CSV format** with fake data. "Today" is fixed to the last date in the data.
- **Conversation history grows without limit**, which is fine for a CLI session but not for long-running use.

## What I'd improve next

- Run the eval across several models and record cost and latency per question.
- Use stricter grading (structured output or an LLM grader with a rubric) alongside the number checks.
- Use more robust anomaly detection (median and MAD), plus recurring-charge and subscription detection.
- Add an importer for real bank CSV exports (run locally only), mapping their columns to this schema.
- Add a Streamlit UI on top of the same agent.
